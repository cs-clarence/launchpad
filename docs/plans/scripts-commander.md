# Move hand-rolled script argument parsing to commander

Audit of every executable script and entry point for hand-rolled argument parsing, and a plan to
move the ones that have real parsing onto `commander` (15.1.0, already in the root catalog and used
by `apps/cli`, `apps/controller` admin and `apps/mcp`).

## Assessment

- **Kind:** medium work. Six existing entry points change their parsing layer; no new feature,
  contract, data or flag. One new shared tooling file and one new root dependency.
- **Risk tier:** two PRs, two tiers. **PR 1** (root dependency, five tooling scripts, helper, docs) is
  Medium: nothing in it runs in a production image, but the root `devDependencies` change touches
  `bun.lock`, which every Docker build installs from, so it is the first commit and is reviewed alone.
  **PR 2** (`apps/router`) is High: the router image runs it (`ENTRYPOINT ["bun","dist/index.js"]`,
  `CMD ["serve"]`, Compose healthcheck `bun dist/index.js healthcheck`). An independent review of this
  plan precedes PR 1; PR 2 gets its own review.
- **How much changes:** PR 1: `tooling/` (five scripts, one new helper), root `package.json`, `bun.lock`
  (regenerated by `bun install`, not by hand), docs. PR 2: `apps/router` (`index.ts`, `package.json`, tests, README), `bun.lock`.
- **Unknowns:** none that block step 1. Measured below: commander's exact behavior for every edge
  case the current parsers handle, and that `bun build` bundles it (the CLI, MCP and admin already
  ship that way).
- **Move up a kind if:** a flag, default, exit code or message has to change to make commander fit
  (the intended behavior changes are the short list under [Behavior that changes](#behavior-that-changes));
  or the router bundle or image behaves differently.

## Goal and done

Every script that parses its own arguments uses commander in the house style
(`new Command().exitOverride().configureOutput(...)`, as `apps/mcp/src/program.ts`), and no script
keeps a hand loop over `argv`. Behavior is preserved: same flags, defaults, positionals, `-a
options="..."` Omni shapes, exit codes and the error wording that tests and docs assert. Done when:

0. each PR is shippable alone: PR 1 leaves the router untouched, PR 2 adds its own manifest
   entries and regenerates `bun.lock` itself. Its one tie to PR 1 is that step 10's check runs
   `tooling/declared-deps.spec.ts`, which PR 1 creates, so PR 2 is opened after PR 1 merges;
1. each converted script passes its existing unit tests unchanged apart from the cases listed under
   [Behavior that changes](#behavior-that-changes), and the new characterization tests (one per row
   of the worked examples) pass;
2. `omni -i run check test build` is green, and the tasks that call each script were run once
   (step tables below);
3. `tooling/local-quickstart.spec.ts`, `tooling/local-deploy-docs.spec.ts` and the router `cli.spec.ts`
   pass with unchanged assertions (the drift tests import only `VALUE_FLAGS`, `SWITCH_FLAGS`, `HELP`,
   `parseArgs` and `main`, all kept);
4. the docs under [Docs to update](#docs-to-update) are current.

### Packaging and dependency facts (checked)

- `commander` is in the root `catalog` but **not** in the root `dependencies`/`devDependencies`:
  `node_modules/commander` is absent at the root, present only under `apps/cli`, `controller`, `mcp`.
  `tooling/` is not a workspace package (no `package.json`), and today imports workspace code by
  relative path (`../packages/client-core/src/index`). A tooling script that imports `commander`
  therefore needs `commander` and `@commander-js/extra-typings` added to the root `devDependencies`
  as `catalog:`; `check-deps` already counts root dependencies as catalog users, so it stays green.
- **Rule: every manifest that imports commander declares it itself**, with the catalog entries
  (`"commander": "catalog:"`, `"@commander-js/extra-typings": "catalog:"`), as `apps/cli`,
  `apps/controller` and `apps/mcp` do. No reliance on hoisting or another package's install.
- **Who imports commander after the refactor** (grep of `apps`, `packages`, `tooling`, imports of
  `commander` or `@commander-js/extra-typings`): `apps/cli`, `apps/controller`, `apps/mcp` (already
  declare both), `apps/router` (new, PR 2) and the tooling scripts (new, PR 1). No other package or
  app needs it: `apps/worker`, `packages/*` have no arguments; `bundle-migrations.mjs` stays
  hand-parsed (decision 3), so `packages/database` gets nothing.
  (`tooling/package-clients.spec.ts` only lists the names as strings.)
- `apps/router` is built with `bun build src/index.ts --target=bun --outdir=dist` (no
  `--packages external`), so commander is bundled into `dist/index.js` and the image needs no extra
  files. It declares both entries in its own `dependencies` (PR 2). The router Dockerfile runs
  `bun install --frozen-lockfile` at the root, so the lockfile is regenerated with `bun install` in
  the same step and the frozen install re-run.
- **Tooling manifest decision: (a) root `devDependencies`.** The tooling scripts have no manifest of
  their own; Bun resolves their imports against the root `package.json`, which already holds the
  tooling's own tools (`oxfmt`, `oxlint`, `vitest`, `typescript`). Rejected (b), a private
  `tooling` workspace package, as out of scope, with this evidence:
    - the bun workspace globs are `packages/*`, `apps/*`, `tests/*`; `tooling` is not among them, and
      adding it changes the lockfile's workspace set for every Docker build;
    - Omni already treats `tooling/**` as a project (`@launchpad-kit/tooling`, `tooling/project.omni.yaml`)
      but `check-deps` (`loadProjects`) and `versions.ts` (`workspaces()`/`sharedWorkspaces()`) walk
      the bun workspace globs, so a new package would be a new project in both: it would need a
      `name`/`version` that `check:versions` demands to equal the shared version, a place in
      `cog.toml`'s `core` group (`include` paths) or an exemption, a matching Omni dependency list,
      and `check-deps` would start enforcing its own import rules on all of `tooling/` (which imports
      other packages by relative path today, e.g. `../packages/client-core/src/index`);
    - `docs/tooling.md` and `docs/patterns/README.md` describe `tooling/` as not a package.
      That is a restructuring for two dependency lines, so it is not done here. `check-deps` counts root
      dependencies as catalog users, so it stays green with (a).
- `bun.lock` is regenerated by `bun install`, never edited by hand (AGENTS.md).

## Scope

In: the six scripts marked **Convert**, one shared tooling helper, root and router dependency
entries, the characterization tests, docs.

Out, on purpose: scripts with no options (`check-*`, `compose-production`, `package-clients`,

## Approach

### Shared helper: `tooling/cli.ts` (built in step 3, with `local-seed`)

`local-seed` is the first real caller and has the hardest cases, so the helper is written there and
reviewed against them; step 1 is the dependency only. Design, which `local-deploy` (step 7) must fit
without change:

```ts
// One table per script: the single source of options.
type Opt = { flag: string; arg?: string; help: string }; // arg set => takes a value
export function toolCommand(name: string, options: Opt[]): Command;
//   exitOverride(); helpOption(false); a declared --help switch; configureOutput discards
//   commander's own error text; allowExcessArguments(); one .option() per table row.
export function flagsOf(options: Opt[]): { value: string[]; switch: string[] };
//   value = the `flag` of rows with `arg`, switch = the rest (with `--help`); both exactly as today's arrays.
export function keyOf(flag: string): string; // commander's camelCase: --database-url-file -> databaseUrlFile
export function optionHelp(options: Opt[]): string; // the aligned option list for HELP
export function parseOrFail<T>(
    program: Command,
    argv: string[],
    fail: (message: string) => Error,
    policy: Policy,
): T; // a cast: see below
```

**Typing:** with a table-driven `.option()` loop `@commander-js/extra-typings` cannot infer `opts()`, so
`parseOrFail<T>` returns `program.opts()` cast to `Record<string, string | boolean | undefined>` (keys
via `keyOf`); the compile-time typing benefit is lost in the helper. The script's `parseArgs` re-validates
and converts the values into its typed `Options`/`Parsed` (defaults, slug/e-mail/number checks), so no
cast leaks out of it.

`Policy` is what makes the wording stay put:

- **`--` terminator:** `argv.includes("--")` throws the script's unknown-option error for `--`
  (both scripts reject it today); nothing after `--` is read as a positional.
- **`-`/`--`-leading values, per option:** `rejectDashValues: "--" | "-"` per script (tooling
  scripts: values starting with `--` throw `<flag> needs a value.`, a single `-x` is accepted, as
  today). Applied after parsing to every option that takes a value.
- **Errors:** `commander.optionMissingArgument` → `<flag> needs a value.`;
  `commander.unknownOption` → the script's unknown-option text with the token taken from commander's
  message; `commander.excessArguments` never fires (excess arguments are allowed and checked by the
  script, below). Any other code → the commander message, so nothing is swallowed silently.
- **Positionals** (`local-deploy`): `.argument("[command]")`; commander accepts options before or
  after it (`--new-key up` works), matching today. The script checks `command` against
  `COMMANDS` and any further argument (`program.args`) and throws today's `Unknown argument <x>.
  Run with --help to list the commands.` For `local-seed`, any argument throws `Unknown option <x>.
  ...`. So no wording depends on commander's `too many arguments` text.
- **`--help`:** a declared switch, never commander's help; `main` prints `HELP`, which is the
  hand-written prose around the generated option list (below).
- **Exit codes** stay the script's: the helper only throws the script's error class
  (`SeedError`, `DeployError`, `Error`); `main` still returns 1; `versions.ts` and `test-db.ts` map
  usage errors to 2 themselves.

No base class, no shared error type. `apps/*` do not import `tooling/`, so the router has its own
small mapping in PR 2.

### Decisions

1. **One option table per script.** The table feeds commander, `VALUE_FLAGS`, `SWITCH_FLAGS` (via
   `flagsOf`) and the option list inside `HELP` (via `optionHelp`); only the prose (usage line,
   intro, closing paragraph) stays hand-written. A flag therefore cannot exist in the parser but be
   missing from the help or the arrays. The exports `parseArgs`, `HELP`, `VALUE_FLAGS`,
   `SWITCH_FLAGS`, `main` keep their names and shapes. The drift tests use exactly those five, so
   they need no change. One thing to check in the step: the generated option list is formatted like
   today's (a spec compares each line of the old `HELP` option block with the generated one), so
   `options=--help` output does not change materially.
2. **Router conversion is a separate PR and droppable.** Node `parseArgs` is not a hand loop; the
   hand-rolled part is the `[command, ...rest]` dispatch, the `USAGE` string and the empty-options
   `parseArgs` idiom. Converting gives one style repository-wide; the cost is a production entry
   point, so it ships after PR 1, preceded by tests pinning the old behavior. If review judges the
   risk not worth it, drop PR 2 and record `node:util parseArgs` as accepted in
   `docs/patterns/README.md`.
3. **Leave `bundle-migrations.mjs`** (one positional, a `.mjs` in a package without commander;
   adding the dependency for one `argv[2]` is not worth it) and **the container-copied experiment
   drivers** (single files without `node_modules`; internal phase names).
4. **Root `devDependencies`, not a `tooling/package.json`.** Making `tooling` a workspace package
   changes the Omni graph, `check-deps`, `tsconfig.tooling.json` and CI.
5. **Router keeps Node's value rule locally.** Commander accepts `--token-file --token-stdin` as a
   value; Node strict mode rejects it, and `init` would otherwise try to read a file named
   `--token-stdin`. The router therefore pre-checks its raw subcommand argv: for the separate-token
   form of `--token-file` and `--database-url-file`, a missing value or a value starting with `-`
   fails with the existing `expected exactly one of ...` text; `--token-file=-x` stays accepted (as in
   Node), then fails later as a bad path. This lives in `apps/router/src/index.ts` (about ten lines).

### Behavior that changes

Intended, harmless, and listed so review can accept or reject each:

- **Tooling scripts:** `--flag=value` is accepted where it was an unknown option; `--org=` is accepted
  and then fails the existing validators. **Not the router** (Node already accepted `--flag=value`).
- **Error precedence with several problems in one argv.** Today the first problem in argv order
  wins (`--org --project --nope` → `--org needs a value.`); commander raises an unknown option
  before the missing-value/validation checks (→ `Unknown option --nope...`). Each message is
  still one of the existing ones, exit code unchanged. Not preserved on purpose.
- `release-dry-run.ts`: an unknown option is now an error (exit 1) instead of silently ignored. That
  includes `-x` and `-h`, which were taken as the output folder name or ignored; `--help` now prints
  the usage line and exits 0 (it used to be ignored and start a rehearsal).
- `versions.ts` (stricter than planned, kept): `check --foo` and `check -x` print the usage line and
  exit 2 (they ran the check and exited 0); `sync <package> --foo` exits 2 with the usage line (it
  took `--foo` as the version and failed on it). The cog hook's `sync <package> <version>` and
  `check` are unaffected. Pinned in `tooling/exit-codes.spec.ts`.
- **Wording when `--` appears anywhere in argv:** `local-seed --org --` reports `Unknown option --.`
  (was `--org needs a value.`) and `local-deploy` reports `Unknown argument --.` (was `Unknown argument --org.`
  when `--` followed a flag it does not know, and `--project needs a value.` when it followed
  `--project`; checked against the old parser), because the terminator is refused before parsing.
- Router (the separate commit in PR 2 only): `serve --help`, `init --help`, `rotate --help`,
  `healthcheck --help` print help and exit 0 instead of a usage error. In the parser-swap commit
  itself a usage error and a bad environment together report the usage error first (the
  environment is read after parsing), and the same precedence note applies to multi-error argv; each
  error alone is unchanged.

Everything else is preserved: every flag, default, validation, message for a single error, exit
code and output stream.

## Risks

- **Router behavior drift (High impact, low likelihood).** A mapping slip changes a message
  operators or scripts match, or an exit code that Compose's healthcheck reads. Mitigation: step 9 pins
  the behavior on the old code first; the healthcheck is `serve`-independent and has exit 0/1 tests
  (`cli.spec.ts` 264-267); built-bundle run and image build in step 10.
- **Undeclared import (Low).** A script could import commander from a manifest that does not declare it and work only through hoisting. `tooling/declared-deps.spec.ts` (step 1) fails on it.
- **Lockfile and image builds (Medium).** A root `devDependency` changes the install every image
  does. Mitigation: step 1 alone, `bun install --frozen-lockfile` re-run, `test:images` and the
  router image build before merge; commander is already part of three bundles, so version and
  resolution are known.
- **Doc-drift tests (Medium, likely if careless).** They read `VALUE_FLAGS`/`SWITCH_FLAGS`/`HELP`
  and `-a options=` strings. Mitigation: the exports are kept, derived from the declared options,
  and a new test fails if an option is missing from `HELP`.
- **Commander accepts what the old parser rejected** (`--flag=value`, `--org=`): accepted widening,
  every value still passes the existing validators; `--org --project` and `--` are rejected as
  before by explicit checks.
- **Shell word splitting through Omni.** `{{ args.options }}` is unquoted; values with spaces were
  never supported (validators reject them). No change, but the examples must run through `omni`
  and not only through `bun` in verification.
- **Exit code 2** in `versions.ts`/`test-db.ts` is easy to lose because commander's default for a
  usage error is 1. Mitigation: covered by the step 2 tests.
